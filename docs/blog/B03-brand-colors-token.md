# B03 · Flutter BrandColors 设计 Token 集中管理，消灭硬编码色值实战，各位同学记得收藏哦！

> 作者：FungLeo ｜ 适用：Flutter / 任意有设计规范的中大型项目
> 目标：把全项目散落的 `Color(0xFF...)` 收敛成一套语义常量，改色只动一处。

### 前言

各位看官，我先问一个问题：打开你现在的项目，全局搜一下 `Color(0xFF`，能搜出多少个？

我第一次认真数的时候，搜出来一百多处。当时挺震撼的——我一直以为自己写得还挺规范。

事情的起因还是 [B01](B01-material3-theme-system.md) 里提过的那次改色。设计同学要把主色往深里调一点点，我全局搜索替换，改完自信满满地交付，结果真机上还是被抓出两处漏网的。

为什么会漏？后来我复盘了一下，原因特别琐碎但特别真实：

- 有的地方写的是小写 `0xff0052d9`，搜大写搜不到；
- 有的地方写的是 `Color(0xFF0052DA)`，末位差一个数，肉眼根本看不出来——多半是当年某位同学（也可能就是我自己）从设计稿上取色手抖了；
- 还有的是 `Colors.blue`，用的是 Flutter 内置色，跟品牌蓝差着十万八千里，但在小面积色块上你真看不出来。

说实话，那次之后我就明白了：**靠"下次注意点"是解决不了这个问题的，得靠机制。**

解法其实一句话：**所有颜色收敛到 `BrandColors` 语义常量，业务代码零硬编码。**

道理简单得很，但落地过程还是有不少讲究，这篇就把我们踩过的坑一起讲了。

### 一、语义色 vs 字面量，差在哪

先看一段坏味道的代码：

```dart
// ❌ 坏味道：三个月后你自己都不知道这几个色是啥
Container(
  color: const Color(0xFFF3F3F3),     // 这是什么灰？和品牌灰底是同一个吗？
  child: Text(
    'xxx',
    style: TextStyle(color: const Color(0xFFA6A6A6)), // 这个灰又是干嘛的？
  ),
);
```

再看好味道的：

```dart
// ✅ 好味道：一眼看懂这块是页面底色 + 次要文案
Container(
  color: BrandColors.surface,
  child: Text(
    'xxx',
    style: TextStyle(color: BrandColors.textSecondary),
  ),
);
```

代码行数几乎一样，但差别是本质的。

字面量只告诉你**"这是什么颜色"**，语义常量告诉你**"这个颜色是干什么用的"**。

这个区别在改色的时候体现得最明显。假设设计同学说"次要文字太浅了，加深一档"，用语义常量的话，你改 `BrandColors.textSecondary` 一处，全站所有次要文字一起变，而页面底色那个灰纹丝不动——因为它们本来就是两个不同用途的常量，哪怕色值曾经很接近。

而用字面量的话……祝你好运。你得一个一个判断这个 `0xFFA6A6A6` 到底是"次要文字"还是"某个恰好也用了这个灰的边框"。

**这也是为什么命名一定要按"用途"，不能按"色值"。**

我早期图省事，命名用的是 `grey1` / `grey2` / `grey3`。后来设计加了一档介于 1 和 2 之间的灰，我得起个 `grey15`……当场就绷不住了。而且 `grey2` 这个名字什么信息都没给你——它既没告诉你该用在哪，也没阻止你把它用在错误的地方。

现在一律按用途命名，名字是长了点，但值。

### 二、一套够用的语义色清单

按我们项目沉淀下来的，一套够用的语义色大概是这些：

| 类别 | 常量 | 用途 |
|------|------|------|
| 品牌 | `primary` / `primaryLight` / `primarySurface` | 主色 / 浅主色 / 选中态浅底 |
| 状态 | `success` / `warning` / `error` | 成功绿 / 警告橙 / 错误红 |
| 文字 | `textPrimary` / `textSecondary` / `textDisabled` | 主文案 / 次要文案 / 禁用态 |
| 背景 | `surface` | 页面灰底 |
| 线 | `line`（分割线）/ `border`（卡片边框） | 1px 分隔 / 输入框边框 |

一共也就十来个，不多吧。

有同学可能会问：为什么不定义得更细一点，比如再拆个 `textLink`、`iconDefault`、`bgHover` 什么的？

我的看法是**够用就好，别提前设计**。语义色这东西，加一个很容易，删一个很难——因为你永远不确定是不是还有哪个页面在用。所以宁可等真的出现了第三处需要这个色的地方，再把它提炼成常量，也别一开始就照着某个大厂设计系统抄一百个 token 进来。那些 token 是给几十个产品线共用的，你一个 App 用不上。

再多说一句 `line` 和 `border` 的区别，这俩色值很接近，容易搞混：

- `line` 用在**分割**上，比如列表项之间那条 1px 的横线；
- `border` 用在**包裹**上，比如卡片外面那圈框、输入框的边。

分开的好处是：有一天设计说"卡片边框太重了想淡一点，但列表分割线保持不变"，你改一个常量就完事。要是当初图省事合成一个 `divider`，这会儿就得先拆再改。

### 三、落地：做一次"颜色收口"专项

清楚了原理，接下来是最现实的问题——**存量的一百多处硬编码怎么办？**

我的答案是：**专项做、批量做，别指望日常开发顺手清。**

这个我是有教训的。最早我在团队群里说"以后大家写代码顺手把看到的硬编码色换掉哈"，结果三个月过去，一共换了不到十处。为什么？因为日常开发的时候，你的注意力在需求上，看到旁边一行硬编码色，第一反应是"这跟我这次改的没关系，别动它，动了还得多测一遍"。这是完全合理的判断，所以指望顺手清，就是永远清不完。

我们最后是排了专门的时间，分几轮做完的。流程如下：

#### 第 1 步：列出所有硬编码点

```sh
# 列出所有硬编码色值，带文件名和行号
➜ grep -rn "Color(0xFF" lib/

# 统计一下总数，心里有个数
➜ grep -rn "Color(0xff\|Color(0xFF" lib/ | wc -l

# 别忘了 Flutter 内置色，这些也是硬编码
➜ grep -rn "Colors\.\(red\|blue\|green\|grey\|black\|white\)" lib/
```

注意这三条命令要都跑。我第一次只跑了第一条，漏掉了大小写混写的和 `Colors.grey` 那一批，白高兴一场。

顺便说个小技巧，按文件统计一下分布，能帮你安排顺序：

```sh
# 看看硬编码主要集中在哪几个文件，从多到少
➜ grep -rc "Color(0x" lib/ --include="*.dart" | grep -v ":0$" | sort -t: -k2 -rn | head -20
```

一般会呈现明显的二八分布——少数几个"老页面"贡献了大部分硬编码。先啃这几个，进度条唰一下就上去了，人也有干劲儿。

#### 第 2 步：逐文件替换，保持视觉零变化

这一步的原则只有一条，我用加粗强调：**只换引用，不调色值。**

意思是，如果某处原本是 `Color(0xFFA6A6A6)`，而 `BrandColors.textSecondary` 恰好就是 `0xFFA6A6A6`，那就直接换。但如果某处是 `Color(0xFFA7A7A7)`（差一点点），**你也要先按最接近的语义色换过去，让视觉保持"看不出差别"，而不是借机把它改成设计稿的标准值。**

为啥这么轴？因为**收口和调色是两件事，混在一起做，review 就废了。**

你想啊，一个 PR 改了五十个文件，reviewer 怎么审？如果规则是"只换引用、视觉零变化"，那他只要确认"换过去的语义色对不对"就行，很快。但如果里面还夹杂着"顺便把这个色调正了"，他就得逐个判断"这处视觉变化是有意的还是手滑"，工作量差十倍，而且一定会漏。

而且视觉零变化还有个好处：**测试同学的回归成本极低。**你可以理直气壮地说"这次改动界面不应该有任何变化，看到任何差异都是 bug"。这个验收标准清晰得不能再清晰了。

#### 第 3 步：争议项单独拎出来

收口过程中，你一定会遇到"对不上"的情况。

我们当时就遇到一个典型的：项目里存在**两个不同的绿色**，一个是 `0xFF2BA471`，另一个是 `0xFF00A870`。翻了半天记录，发现是两个时期的设计稿给的值不一样，后来也没人统一过。

这种事儿怎么处理？我的做法是：

1. **不在收口 PR 里做决定。**先临时都指向现有的 `BrandColors.success`，或者干脆保留原样加个 `// TODO: 双绿待统一` 标记，让收口 PR 保持"视觉零变化"这个干净的属性。
2. **单独开一条记录**，写清楚：哪两个色、分别用在哪些页面、各自的来源。
3. **单独找设计同学决策**，定了之后再单独提一个 PR，这个 PR 明确就是"改视觉"的，让测试重点回归。

这么做看着麻烦，其实是最省事的。把"机械替换"和"需要决策"的东西分开，每一件事的性质就都清楚了。混在一起的话，一个卡住，全部卡住。

#### 第 4 步：把规则写进规范文档

最后一步，也是最容易被跳过的一步：**在团队的 UI 规范文档里写死规则。**

> **禁止在业务代码中硬编码色值，所有颜色必须引用 `BrandColors.*`。**

为什么这一步不能省？因为你辛辛苦苦清完一百处，如果没有规则约束，下个月又会冒出三十处新的。新同学不知道有 `BrandColors` 这个东西，他从设计稿取个色就写进去了，这太自然了，怪不着人家。

规则写进文档，新人 onboarding 的时候看一遍，code review 的时候有据可依，这事儿才算长久。这块的更多想法可以看 [G01](G01-style-guide-hard-rules.md)。

### 四、能不能让机器帮忙盯着？

上面第 4 步是靠"人"来守规则的，那能不能更自动一点？

这里我得先泼盆冷水：**Dart / Flutter 官方的 lint 规则集里，并没有一条现成的"禁止硬编码颜色"规则。**我翻过 `flutter_lints` 的清单，确实没有。所以别去 `analysis_options.yaml` 里瞎试规则名了，试不出来的。

现实一点的做法有这么几种：

**方案一：CI 里加一条 grep 检查。**最土也最有效，五分钟就能加上：

```sh
#!/bin/sh
# scripts/check_hardcoded_color.sh
# 检查 lib/ 下是否有新增硬编码色值（theme 目录除外）
if grep -rn "Color(0x" lib/ --include="*.dart" | grep -v "^lib/theme/"; then
  echo "❌ 发现硬编码色值，请改用 BrandColors 语义常量"
  exit 1
fi
echo "✅ 颜色检查通过"
```

注意那个 `grep -v "^lib/theme/"`——`theme` 目录本来就是定义色值的地方，得放行，不然自己拦自己。

**方案二：用 `custom_lint` 写自定义规则。**能力更强，能给出编辑器内的实时提示，体验好很多。但要写 Dart 分析器插件，有一定门槛，而且维护成本不低。我个人感觉，对大多数项目来说这属于脱裤子放屁，方案一的 grep 已经能挡住 95% 的情况了。

**方案三：什么都不加，靠 code review。**别笑，如果团队就三五个人，这个方案是真的够用。规则写清楚，review 的时候扫一眼 diff 里有没有 `0xFF`，成本几乎为零。

我们最后选的是方案一 + 方案三的组合。够用就好，没必要太折腾。

### 小结

好啦，颜色收口这事儿就聊到这。核心的几条给各位看官捋一捋：

1. **颜色收口要专项做、批量做**，不要指望日常开发顺手清——真的会永远清不完，我试过了。
2. **语义色命名用"用途"（`textSecondary`），不要用"色值"（`grey6`）**，否则换个灰又得加常量，而且名字本身不带任何约束力。
3. **收口时保证视觉零变化**，只换引用不调色值。这能把 review 和回归的成本压到最低。
4. **调色这种有争议的事单独拎出来**，别混进机械替换里，一混就全卡住。
5. **规则要写进规范文档才长久**，有余力的话再补一条 CI grep 检查兜底。
6. 语义色**十来个就够用**，别照着大厂设计系统抄一百个 token 进来，用不上还添乱。

说实话，这活儿一点都不"高级"，纯粹是体力活加细心活。但它带来的收益特别实在——现在设计同学再说要调色，我改一行常量，五分钟交付，心里踏实得很。
