# B02 · Flutter 第三方 UI 库渐进迁移 Material 3，组件映射总表与分批替换策略，必看！

> 作者：FungLeo ｜ 适用：Flutter 3.x / Material 3
> 场景：项目早期引入的第三方 UI 库不太稳，想换回原生 M3，但又不敢一刀切。

### 前言

接着 [B01](B01-material3-theme-system.md) 的主题四件套往下讲。

我们项目早期是引了一套第三方 UI 库的（TDesign Flutter，0.2.x 版本）。当时的想法很朴素：现成的组件拿来就用，能省不少时间，何必自己造轮子。

一开始确实爽。但用了一段时间，问题陆陆续续冒出来了：

- 某些组件在 Android 上会白屏，换个机型又好了，很难稳定复现；
- 小版本升级之间 API 会变，升一次得改一圈调用；
- 组件的视觉细节跟我们的设计稿对不齐，改吧改不动（样式没暴露出来），不改吧设计同学天天来找；
- 最要命的是，出了问题只能等上游修，自己插不上手。

那段时间我挺纠结的。说实话，一开始我是想"再忍忍"的，毕竟迁移的工作量摆在那儿。但后来算了笔账——每个月因为这套库损耗的排查时间，其实已经超过一次性迁移的成本了。

于是决定：**整体迁回 Material 3 原生 + 自研公共组件**。

但这种"换 UI 底层"的活儿，最忌一次性全改。我见过有团队开个大分支 all in，改了三周，合回主干的时候冲突炸裂，测试还没法测——因为整个 App 都变了，根本不知道该重点回归哪儿。

所以我用的是**渐进式四批次替换**。这篇就把整个过程完整记一下。

### 第一步：先扫描，把家底摸清楚

动手之前，先搞清楚要改多少东西。别凭感觉，凭感觉估出来的工作量一般能差个三倍。

我的做法是直接 grep 全项目，统计每个三方组件的出现次数：

```sh
# 统计每个组件的出现次数，从多到少排序
➜ grep -rho "TD[A-Za-z]*" lib/ | sort | uniq -c | sort -rn

# 想看某个组件具体分布在哪些文件，加 -l
➜ grep -rl "TDButton" lib/
```

跑出来大概是这么个分布：

```sh
🔴 TDButton（~15 处）、TDToast（~20 处）  # 高频，影响面最广
🟡 TDTextarea（3）、TDPicker（2）、TDStepper（2）、TDNavBar（1）  # 中频
🟢 TDIcons（~20 个不同图标名）           # 纯图标，最好换
```

这张表出来之后，心里就有底了：真正麻烦的不是数量，而是**高频组件牵一发动全身**。`TDToast` 有二十处，散落在各种异步回调里，改错一个可能就是线上一个静默失败。

据此我排了替换优先级，并产出一张**组件映射总表**——每个旧组件对应换成什么、示例代码长什么样，都提前写清楚。

### 第二步：产出组件映射总表

这一步我强烈建议做，而且要写成文档存下来，不要只存在脑子里。

为啥？因为迁移不是一天干完的，中间会被别的需求打断。等你三天后回来，早忘了上次决定 `TDPicker` 要换成什么了。而且如果是多人协作，没有这张表，两个人会替换出两种不同的写法，那还不如不迁。

表大概长这样（节选）：

| 旧组件 | M3 / 自研替代 | 备注 |
|--------|---------------|------|
| `TDIcons.xxx` | `Icons.xxx` | 一一对应，最简单 |
| `TDButton`（主按钮） | `FilledButton` | 圆角走 [B01](B01-material3-theme-system.md) 的主题覆写 |
| `TDButton`（次按钮） | `OutlinedButton` / `TextButton` | 按视觉层级选 |
| `TDToast` | 自研 `AppToast` | 统一入口，见 [B04](B04-public-widget-library.md) |
| `TDAlertDialog` | 自研 `AppDialog.confirm` | 收敛掉 builder 样板 |
| `TDNavBar` | `AppBar` | 主题里已统一样式 |
| `TDTextarea` | 自研 `AppTextarea` | 带字数计数浮层 |
| `TDPicker` | `showModalBottomSheet` + 自绘 | M3 无直接对应 |
| `TDStepper` | 自绘 | M3 无直接对应 |

映射表里有几个坑，我提前说一下：

**一是"一对多"的情况。**像 `TDButton` 这种，第三方库常常用一个组件加 `type` 参数搞定所有按钮形态；而 M3 是拆成 `FilledButton` / `OutlinedButton` / `TextButton` 三个独立组件的。所以你不能无脑替换，得**一处一处看它原来是什么形态**。这是整个迁移里最费眼力的部分。

**二是"没有对应物"的情况。**像步进器、日期选择器这些，M3 压根没提供或者提供的形态不合适，只能自绘。这部分工作量最大，所以要单独排批次，别混在常规替换里。

**三是行为差异。**这个最阴险。比如三方 Toast 可能是"自动排队、后一个等前一个消失"，而你用 `ScaffoldMessenger` 自己实现的可能是"后一个直接顶掉前一个"。视觉上都是弹个提示，但在批量操作的场景下表现完全不同。这种差异 `flutter analyze` 是查不出来的，只能靠真机点。

### 第三步：先搭"替代品"，再动手替换

这条是我最想强调的：**不要边删边想新写法。**

我一开始就是这么干的，删掉一个 `TDToast`，现场想"那我用什么呢"，然后随手写了个 `ScaffoldMessenger.of(context).showSnackBar(...)`。改到第五处的时候，我发现前面四处的样式、时长、位置全都不一样——因为每次都是现场发挥的。

正确的顺序是：

1. 先按 [B01](B01-material3-theme-system.md) 把主题四件套搭好，让原生组件的样式先对上设计稿；
2. 再按 [B04](B04-public-widget-library.md) 把公共组件抽出来（`AppDialog` / `AppBottomSheet` / `AppSearchBar` / `AppToast` 这些）；
3. 把这些新组件放进一个 preview 分支，专门做一个测试页，把所有形态都摆出来验一遍；
4. **确认组件质量过关，再回主干逐页替换。**

这样替换的时候你就是个"体力活工人"，机械地把旧的换成新的，不需要动脑做设计决策。脑子越不需要动，出错的概率越低，这活儿也才能安心交给别人一起干。

### 第四步：四批次渐进替换

批次是按**风险**排的，不是按工作量排的：

| 批次 | 内容 | 风险 |
|------|------|------|
| 1 | 主题搭建 + 组件测试页 | 低 |
| 2 | 低风险：图标 `Icons.xxx` / `AppToast` / `AppDialog` | 低 |
| 3 | 中风险：搜索栏 / 表单区块 / 底部操作栏 | 中 |
| 4 | 自绘：步进器、日期选择器等无直接 M3 对应的 | 中 |

这里有个反直觉的点，我当时也想了一会儿：**高频组件（Button / Toast）影响面最大，为什么反而放在靠后的批次？**

因为影响面大，就意味着一旦替代品有问题，波及的页面也最多。你得先让替代品在小范围里跑一段时间，确认没毛病了，再拿它去铺二十个页面。要是反过来，先铺二十个页面，然后发现替代品有个边界问题，你就得再改二十遍。

每一批替换完，跑一遍静态检查再上真机：

```sh
# 静态检查，先把编译期和 lint 的问题清掉
➜ flutter analyze

# 真机跑一遍，重点看这一批涉及的页面
➜ flutter run
```

关键是：**单批可独立回滚。**每批单独提交、单独合并，万一哪批出问题，`git revert` 掉那一个提交就行，不影响其他批次的成果。这就是渐进式最大的价值，不是改得快，而是**出事的时候退得起**。

### 第五步：彻底移除依赖

全量替换完成、并确认没有残留之后，才轮到从 `pubspec.yaml` 里删依赖：

```yaml
dependencies:
  flutter:
    sdk: flutter
  # 移除这行（迁移完成后）
  # tdesign_flutter: ^0.2.7
```

```sh
➜ flutter pub get
➜ flutter clean && flutter build apk   # 完整重建一次，确认没有编译残留
```

但在删之前，一定要把"零残留"确认干净。这里我有个教训：

> 确认"零残留"要用 `grep` 扫**整个源码**，而不是只看"还有没有 import"。因为有些地方 import 已经删了，但注释里、字符串里、甚至某个 `// TODO: 改成 TDPicker` 里还留着旧名字。这些不影响编译，但会误导后面接手的人。

```sh
# 扫源码，包括注释和字符串
➜ grep -rn "tdesign\|TDesign\|TD[A-Z]" lib/

# 别忘了 pubspec.lock 和各平台目录也扫一眼
➜ grep -rn "tdesign" pubspec.lock ios/ android/
```

还有一个容易忘的：**删依赖之后一定要完整重建一次，而不是热重载。**因为热重载不会重新解析依赖，你可能改完看着一切正常，等 CI 上一跑才发现某个文件还在引用已删的包。我就这么被 CI 打过一次脸。

### 那我当初到底该不该引这个库？

聊到这儿，各位看官可能会问：那是不是一开始就不该用第三方 UI 库？

我觉得不能这么说。事后诸葛亮谁都会当，但当时那个决策在当时的信息条件下是合理的——项目要快速出原型，用现成组件确实省了不少时间。

我现在的判断标准大概是这样：

- **短周期项目 / 原型验证**：用三方库，快就是一切，反正也不长期维护。
- **长期维护的项目**：如果这个库版本号还在 0.x，社区活跃度一般，那就要谨慎了。0.x 意味着作者保留随时改 API 的权利，这是人家明说了的。
- **设计规范强的项目**：三方库的样式定制能力是关键。如果它没暴露足够的样式钩子，你迟早会撞墙。

至于"要不要自己造轮子"，我的看法是：**别造完整的 UI 库，但可以造一层薄薄的封装。**像 [B04](B04-public-widget-library.md) 里那种基于原生 M3 的公共组件，代码量不大，完全可控，出了问题自己就能改。这个投入产出比，我觉得是划算的。

### 小结

好啦，这套迁移就复盘到这里。核心的几条：

1. **迁移 = 先有替代品，再替换**，千万不要裸删。删了再想写法，等于把设计决策塞进体力活里，必乱。
2. **动手前先 grep 摸底 + 产出组件映射总表**，把决策前置，替换阶段才能机械化推进。
3. **渐进四批次，按风险排序**，每批可验证、可回滚，避免"大爆炸式重构"。
4. **高频组件放靠后批次**。影响面越大，越要等替代品稳了再动。
5. **移除依赖是最后一步**，且要 grep 扫全量源码确认零残留，完整重建验证。
6. 三方库不是不能用，但**长期项目要看版本号和定制能力**，0.x 版本心里要有数。

回头看，这次迁移最大的收获其实不是"用上了 M3"，而是**把 UI 的控制权拿回到了自己手里**。以前遇到样式问题只能提 issue 等着，现在打开自己的组件文件改两行就完事了。这种踏实感，值。
