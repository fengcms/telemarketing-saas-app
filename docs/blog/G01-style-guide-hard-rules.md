# G01 · 用 STYLE_GUIDE 固化三条硬规则，单文件 560 行红线实战，各位同学记得收藏哦！

> 作者：FungLeo ｜ 适用：Flutter / 团队协作 / 工程规范
> 主题：把"口头约定"变成"可机器核验的硬规则"，并用代码审查守住它。

### 前言

说实话，这事儿我一开始是不当回事的。

项目做到中后期，我在代码审查里发现了几个反复出现的问题：文件动不动一千行、一条紧急修复里夹着五六件杂事、commit message 上来就是"统一重构全部页面"。每次我都在群里说一句"下次注意哈"，对方也回一句"好的好的"。

结果呢？下一轮审查，同样的问题又回来了。一模一样。

我后来想明白了：**口头约定是会回摆的**。不是大家不认真，是人脑记不住这种"软性共识"，尤其是赶进度的时候，第一个被牺牲的就是它。所以从某一版开始，我改了打法——把最关键的几条规则，白纸黑字写进 `STYLE_GUIDE.md`，每条带章节号，然后在代码审查里**逐条核验**，不通过就不放行。

规则不用多，贪多嚼不烂。我们最后只沉淀了三条真正扛用的，今天就跟各位看官唠唠这三条是怎么来的、怎么落地的。

### 为什么非要"写进文档"

先说清楚一个我自己的认知转变。

我以前觉得，规范文档这种东西就是摆设，写了也没人看，属于典型的"脱裤子放屁"。直到我把它和**代码审查**绑在一起，才发现完全是两码事：

- 规则写进文档，它就有了**编号**。审查时我不用长篇大论讲道理，直接甩一句"这条不符合 §2.3"，对方一查就明白，沟通成本几乎为零。
- 规则写进文档，它就变成了**共识而不是我的个人偏好**。不然容易变成"组长今天心情不好"，特别伤协作氛围。
- 规则写进文档，它才可以被**迭代**。发现新坑就补一条，废掉的就删掉，有版本可追。

一句话：文档本身不产生约束力，**文档 + 审查门禁**才产生约束力。这两个缺一个都白搭。

### 规则一：单文件行数红线（560 行）

第一条，也是我认为收益最大的一条：

```text
§2.3 单文件行数红线（560 行）
- 硬性上限，wc -l 统计，含注释与空行
- 新建 / 既有文件超限一律拆分，不设例外
- 确须放宽，须全体讨论后修改阈值并写入本节
```

#### 为什么要卡这个

各位看官应该都见过那种一千多行的详情页 `StatefulWidget` 吧？我见过，还是我自己写的。那玩意儿的问题不是"看着吓人"，而是：

- **读不动**。想改一个按钮的间距，得先滚三分钟找到它在哪。
- **审不动**。一个 PR 改了这文件的 40 行，diff 上下文全是噪音，审查基本靠猜。
- **测不动**。逻辑和 UI 糊在一起，想给某段状态流转写个单测，根本抽不出来。

配合 [D02](D02-part-extension-split.md) 里讲的 `part` / extension 拆分术，这条红线就是守住代码规模的最后一道底线。

#### 560 这个数字是怎么来的

有同学可能会问：为啥是 560，不是 500 也不是 600？

说实话，这数字没什么高深的科学依据哈。我们是先统计了一遍当时仓库里所有源码文件的行数分布，发现大多数写得还算克制的页面文件都落在 400 行以内，而"已经开始让人头疼"的那批基本都超过了 600。取了个中间偏上的值，留出一点缓冲，就定了 560。

我想说的是：**阈值具体是多少不重要，重要的是它是一个确定的数字**。只要它是确定的，就能被机器核验；一旦写成"文件不宜过长"，那就等于没写。

#### 怎么核验

这条规则最大的好处，就是一行命令就能查：

```sh
# 找出 lib 目录下所有超过 560 行的 dart 文件
$ find lib -name "*.dart" | xargs wc -l | awk '$1 > 560 && $2 != "total" {print $1" "$2}'
```

审查的时候我就跑这一句。文档里写"已拆分"没用，命令跑出来是空的才算数。

嫌手动跑麻烦的，可以挂个 pre-commit 钩子，提交前自动拦：

```sh
#!/bin/sh
# .git/hooks/pre-commit —— 简易行数红线检查
# 只检查本次暂存的 dart 文件，不拖慢提交
files=$(git diff --cached --name-only --diff-filter=ACM | grep '\.dart$')
[ -z "$files" ] && exit 0

over=$(echo "$files" | xargs wc -l 2>/dev/null | awk '$1 > 560 && $2 != "total" {print "  "$2" ("$1" 行)"}')
if [ -n "$over" ]; then
  echo "以下文件超过 560 行红线，请先拆分再提交："
  echo "$over"
  exit 1
fi
```

小提醒：上面这段在 macOS 自带的 BSD `xargs` 下也能跑；如果你在 Linux 上习惯写 `xargs -r`，注意 macOS 是没有 `-r` 这个参数的，直接去掉就行。另外记得给钩子加执行权限：

```sh
$ chmod +x .git/hooks/pre-commit
```

### 规则二：阻塞级修复必须独占提交

第二条，是被真事儿逼出来的：

```text
§8.2 阻塞级 / 发布阻断修复必须独占提交
- 适用于：release 装不上 / 起不来 / 核心流程断掉的修复
- 不得与功能开发、样式调整、文档、工具脚本混在一起提交
- 目的：便于 cherry-pick / revert / bisect
```

#### 我们是怎么被坑的

当时有一个"发布包功能不可用"的严重问题，根因就是一行权限声明（这个坑我在 [A01](A01-release-internet-permission.md) 里专门写过）。修是很快修好了，问题出在提交上——那位同学顺手把手上的五六件杂活儿一起提交了：改了两个页面的间距、补了段文档、还顺便动了个工具脚本。

于是这条提交变成了一个"厨房水槽"，什么都往里扔。

坏处马上就来了。发布分支想单独把这条修复摘过去，一 `cherry-pick` 把那些无关改动全带上了：

```sh
# 只想要那行权限修复，结果连带把样式和脚本一起摘了过来
$ git cherry-pick <commit-hash>
```

后来那批样式改动被发现有问题，想干净回滚，又发现回滚会把关键修复一起撤掉：

```sh
# 一 revert 就把救命的修复也一起还原了，很尴尬对吧
$ git revert <commit-hash>
```

再后来用 `git bisect` 定位另一个偶发问题，二分到这条提交时直接卡住了——它同时动了太多东西，根本判断不了"好"还是"坏"：

```sh
$ git bisect start
$ git bisect bad          # 当前版本有问题
$ git bisect good v1.2.0  # 这个版本是好的
```

一条混杂提交，把 Git 三大救命工具全废了。这代价我觉得挺贵的。

#### 落地的判断标准

我给的判断很简单：**这条改动如果单独摘出去发到线上，是不是自洽且安全的？** 是，就单独提交；不是，说明你混了别的东西进去，拆开。

功能开发我不强求，改点样式顺手带个文案我也认。但只要是"阻塞发布"级别的修复，一律独占一条提交，没得商量。

### 规则三：commit message 措辞如实（禁绝对词）

第三条看着最"虚"，但我个人非常在意：

```text
§8.2 commit message 措辞如实
- 禁用「全部 / 统一 / 重构 / 彻底」等绝对词
- 除非确实 100% 覆盖，否则如实写清改动范围
```

#### 起因

有一次我看到一条提交写着"统一全部页面颜色规范"，心里挺高兴，觉得这活儿干得漂亮。结果随手一 `grep`：

```sh
# 检查是否还有硬编码颜色残留
$ grep -rn "Color(0xFF" lib --include="*.dart" | wc -l
```

好家伙，还剩几十处。实际改的只是列表页里的三处硬编码色。

那一刻的感受不是"生气"，而是**"这个仓库的提交记录，我以后不敢信了"**。这才是真正的损失。commit message 是要陪着项目走好几年的东西，将来有人排查问题、追溯变更，全靠它。它一旦掺水，整条历史的可信度就打折。

#### 怎么写才算"如实"

对比一下就很清楚了：

```text
# 不好的写法（夸大，实际只改了 3 处）
fix: 统一全部页面颜色规范

# 好的写法（范围明确，可核验）
fix: 修复列表页 3 处硬编码颜色，改用主题色常量
```

后者读起来一点也不"高级"，但它诚实、具体、可核验。说实话，我宁可看一百条朴实的提交，也不想看一条吹上天的。

顺带一提，这条规则跟写技术文档其实是一回事儿——少用"众所周知""毫无疑问""彻底解决"这类词，留点余地，反而更让人信服。

### 怎么让规则真正落地

规则定完了，怎么让它不变成摆设？我的四步：

1. **规则要从审查里长出来，不能凭空拍**。这三条无一例外，都是先在审查中反复撞见（"红线被冲破 3 处""厨房水槽式提交""message 绝对词夸大"），才被固化成条文的。凭空定的规则，大家心里不服，执行就打折。
2. **写进 `STYLE_GUIDE.md`，每条带章节号**。方便在审查意见里直接引用，省掉大量重复解释。
3. **审查时逐条核验，不接受"文档声明"**。文档说"已拆分"，我就真去 `wc -l`；说"已全改"，我就真去 `grep`。这一条是灵魂，展开讲在 [G03](G03-code-review-loop.md)。
4. **规则本身也允许迭代**。发现新坑就补一条，某条被证明不适合当前阶段，就拿到台面上讨论后改阈值、改措辞，写清楚为什么改。

另外提醒一句：规则别贪多。我见过有团队一上来写了三十几条规范，结果没人记得住，最后一条都没落实。**三五条能被真正执行的硬规则，胜过三十条躺在文档里吃灰的建议。**

### 小结

好啦，这三条硬规则的来龙去脉就讲完了。

回头复盘，这套东西真正起作用的地方，其实不在"规则"本身，而在两个特征上：一是**可机器核验**——行数能 `wc -l`，残留能 `grep`，是否独占提交能看 diff，全都不靠"我感觉差不多"；二是**和审查绑死**——文档只负责定义，审查负责执行，两条腿走路才站得住。

至于阈值定 560 还是 500，措辞禁哪几个词，这些都是次要的，各位看官完全可以按自家项目的情况调。够用就好，没必要照抄。

那么各位看官，您那边是怎么守住代码规范的呢？是靠 CI 卡、靠钩子拦，还是靠组长盯？欢迎在评论区聊聊，我挺想学两招。如果这篇对你有点用，麻烦用您发财的小手点个赞、收个藏哈，谢谢大家！
