# G03 · 组长视角代码审查闭环四阶段，初审→修复→复审→放行实战，各位同学记得收藏哦！

> 作者：FungLeo ｜ 适用：Flutter / 代码审查 / 团队协作
> 主题：一套把 AI 产出的代码从"能跑"拉到"可信"的四阶段审查闭环。

### 前言

和 AI 协作以后，代码来得又快又多。快是真快，但随之而来的问题是——**审不过来**。

一开始我的审查方式很朴素：它说改完了，发我一份修复说明文档，我一看，条条都打了勾，"✅ 已修复""✅ 已拆分""✅ 已全部替换"，看着挺舒服的，我就放行了。

直到有一次我随手核了一下。

那份文档白纸黑字写着"所有源码文件均已控制在 560 行以内"，我顺手跑了一句 `wc -l`，结果蹦出来一个 612 行的文件。就是那次拆分之后，后续又加了功能，涨回去了，但文档没跟着更新，勾还照打不误。

说实话，我那会儿倒不觉得是谁在故意骗我。AI 不会撒谎，它只是**把"我打算做到"当成了"我已经做到"**；人也一样，改完最后一处的时候，脑子里那个勾就自动打上了。

但从那次开始我立了个规矩：**审查不看声明，只看代码。** 后来这规矩慢慢长成了一套四阶段的闭环，跑了几轮下来还挺扛用的，今天分享给各位看官。

### 四阶段闭环总览

先上全景：

```text
① 初审（质量门禁）  → 看整体、给评级、列问题清单
② 修复              → 针对清单逐条改
③ 复审（逐条核验）  → 不看文档声明，去代码里真查
④ 放行              → 确认闭环、归档索引
```

四步里面，第三步是灵魂，也是最容易被跳过的一步。很多团队的审查其实只有 ①②④，中间那步复审直接用"对方说改完了"顶替了，于是审查就变成了走过场。

### 阶段一：初审（质量门禁）

初审的定位是**门禁**，不是挑刺。

拿"一批新增的公共组件"举例。这种审查我不看"替换率完成了多少"这种进度指标，进度好看不代表东西能用。我是**逐个组件判质量**，每个都过这么几问：

- **主题一致吗？** 有没有硬编码颜色、字号，是不是走的统一常量。
- **API 干净吗？** 参数是不是最小必要，有没有那种"传进去也不知道干啥"的开关。
- **生命周期正确吗？** 控制器、监听器、动画有没有在 `dispose` 里释放干净。
- **边界处理了吗？** 空数据、超长文本、极端尺寸下会不会直接崩掉或者溢出。

输出两样东西：一个整体评级（比如 A−），一份问题清单，每条标状态：

```text
✅ ItemCard        通过
✅ ItemTag         通过
🟡 ItemActionBar   暂不通过：7 处颜色硬编码；未处理超长文案溢出
🟡 ItemEmptyView   暂不通过：禁用态色值写死
```

规矩是：**🟡 状态的组件，不准进入后续的替换流程。** 这一条很重要。要是带病的组件先被铺到几十个页面里去了，后面再改就是灾难现场了。

### 阶段二：修复

这一步反而最简单，照着清单改就行，没什么可展开的。

比如上面那个 `ItemActionBar`，7 处硬编码颜色全部换成主题色常量；`ItemEmptyView` 里写死的禁用态色值，换成语义化的常量。改完之后同步更新修复说明文档，标明每条对应改了哪个文件。

唯一要强调的是：**修复说明里别写绝对词**。"全部替换""彻底重构"这种话，除非你真的 100% 覆盖了，否则复审一查就露馅，特别伤信任。这条后来被固化成了硬规则，详见 [G01](G01-style-guide-hard-rules.md)。

### 阶段三：复审（这一步最容易被糊弄）

重点来了。**文档说"已修" ≠ 真修**。

我不是不信任协作方，而是这里存在一个客观的认知偏差：写文档的人凭记忆打勾，而记忆是会出错的，尤其是改动分好几天完成的时候。所以复审必须去代码里逐条核验，一条都不能跳。

#### 用命令核验，别用眼睛核验

关键在于，**核验动作要能落到命令上**。眼睛扫一遍等于没审。举几个我常用的：

```sh
# 文档说"560 行红线已守住" —— 那就真去看行数
$ find lib -name "*.dart" | xargs wc -l | awk '$1 > 560 && $2 != "total" {print $1" "$2}'
```

```sh
# 文档说"7 处硬编码颜色已全改" —— 那就真去搜残留
$ grep -rn "Color(0xFF" lib --include="*.dart"
```

```sh
# 文档说"旧组件已全部下线" —— 那就真去搜引用
$ grep -rn "OldItemCard" lib --include="*.dart"
```

```sh
# 顺手看一眼这批改动到底动了哪些文件，和文档描述的范围对不对得上
$ git diff --stat HEAD~1
```

各位看官发现规律没有？**能被 `grep` 和 `wc` 验证的规则，才是好规则。** 反过来说，如果一条规范你根本想不出该怎么核验它，那它多半就是一句正确的废话，写了也是白写。

这也是为什么我们定规则的时候，宁可定"单文件不超过 560 行"这种看起来很死板的数字，也不定"文件不宜过长"这种听起来很有道理的表述。

#### 查出问题不实，怎么办

就是前言里那个 612 行的文件。文档写着"所有文件 ≤560"，实际有一个超了。

我的处理方式是：**当场纠正文档，不包庇。** 具体三步——把那条勾撤回来，注明"经复审核实，某文件为 612 行，未达标"，然后重新回到阶段二。

我知道这么干有点不给面子，但我觉得这是审查最不能让步的地方。**你放过一条，整份文档的可信度就归零了。** 后面所有的勾，别人都得重新核一遍，那这文档还有什么意义？

这一步筛掉的"声明式修复"，数量比我预想的多得多。

#### 复审清单可以固定下来

跑几轮之后，复审清单基本就稳定了，我一般固定核这几项：

| 核验项 | 手段 |
|--------|------|
| 单文件行数 | `wc -l` 全量扫 |
| 硬编码色值 / 字号残留 | `grep` 关键模式 |
| 旧组件是否真下线 | `grep` 类名引用 |
| 改动范围与文档是否一致 | `git diff --stat` |
| 阻塞级修复是否独占提交 | 看 commit diff |
| 生命周期释放 | 人工看 `dispose` |

前五项都能命令化，剩下一项才需要人工看。这么一分，复审的时间成本其实不高，跑一遍也就几分钟的事儿。

### 阶段四：放行 + 归档

全部核实为真修之后，才进入放行。

放行不是口头说一句"过了"就完了，得留下痕迹：产出一份"放行确认"文档，写清楚这次审了什么、发现了哪些问题、最终结论是什么；然后在索引（一般就是 README）里更新状态。

为什么要归档？因为**审查记录本身就是资产**。三个月后有人问"这个组件当初为什么这么设计"，翻出来一看审查记录，答案就在那儿。不然全靠人脑记，记不住的。

### 审查中沉淀的硬规则

最后说个我觉得最有意思的点：**审查不只是找问题，它还是规则的来源。**

同一类问题出现三次以上，就说明这不是个人失误，而是缺规则。我们那三条硬规则（见 [G01](G01-style-guide-hard-rules.md)）全是这么来的：

- 审查中发现"560 红线被冲破 3 处" → 固化成**单文件行数红线**
- 审查中发现"厨房水槽式提交" → 固化成**阻塞级修复独占提交**
- 审查中发现"message 用绝对词夸大" → 固化成**commit 措辞如实**

这就形成了一个正循环：审查发现问题 → 固化成规则 → 规则自动守门 → 下次审查不用再管这类问题，腾出精力去看更深的东西。

反过来，如果审查只是每次挑一堆刺、改完就完，那你就得永远盯着，累死也盯不过来。

### 小结

好啦，这套四阶段闭环就讲完了。

复盘一下，整套东西其实就守住了一个原则：**不接受"声明式修复"**。文档说改了不算数，命令跑出来干净才算数。这话听着有点不近人情，但代码这东西就是这样，它不看你说了什么，只看你写了什么。

另外我想说，这套流程不是只对 AI 有用。人写的代码同样会出现"以为改完了其实没改完"，只不过和 AI 协作时代码量大、节奏快，这个问题被放大了而已。

当然，也不是所有项目都值得上这么一套。小项目、短生命周期的东西，别折腾，够用就好。
