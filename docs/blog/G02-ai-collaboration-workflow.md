# G02 · 与 AI 协作开发完整 App 的实战流程，读文档→提问→计划→开发→实测→提交，必看！

> 作者：FungLeo ｜ 适用：Flutter / AI 辅助开发 / 团队协作
> 主题：一套能把 AI 的"快"和人的"把关"结合起来的七步工作流。

### 前言

这篇聊点"软"的，不贴什么源码，讲的是我和 AI 编程助手协作，从零开发一个完整移动端 App 的**工作流**。

说实话，一开始我对这事儿是有点轻敌的。我想着无非就是"我说需求、它写代码、我看一眼",能有多难。第一天我就让它把一整个模块都撸出来，结果收获了两个惊喜：

第一个惊喜是快。是真快，一顿操作猛如虎，页面转眼就跑起来了。

第二个惊喜是……我打开文件一看，一千多行。UI、状态、数据处理全糊在一个文件里，我改个东西得先滚半天鼠标。更要命的是，里面有几个数据字段的名字，我怎么看怎么眼生——一对文档才发现，那几个字段它是**自己编的**。它没查到，但它也没说"我不确定"，而是非常自信地写了个看起来很合理的名字。

那次我被打脸打得挺清醒的：**AI 的问题从来不是写得慢，而是它不知道自己不知道**。你不给它划边界，它就会用"看起来很对"的东西把空白填满。

后来我就慢慢磨出了一套流程。现在回头看，这套流程的核心其实就一句话：**别指望 AI 自觉，靠流程把关卡设好。** 分享给各位看官参考。

### 我们最终定下来的七步流程

先把结论摆出来，这七步是写死在协作规则里的：

```text
1. 每次最多开发一个页面（控制变更粒度）
2. 开发前读透设计文档，从接口文档里找出对应接口
3. 接口返回结构不清晰、字段不明 → 必须提问确认，不许猜
4. 先写开发计划文档，等我确认后再进入开发
5. 开发完成 → 要求我真机实测并反馈
6. 确认没问题 → 写进度文档、踩坑文档
7. git commit & push
```

看着挺啰嗦对吧？我一开始也觉得。但实际跑下来，这七步里每一条都是拿返工换来的。下面挨个说说为什么。

### 为什么这套流程扛用

#### 1. 小步快跑，一次只交付一个页面

"每次最多一个页面"这条，是直接冲着我前面那次一千行的教训去的。

粒度小有三个好处：变更可验证（这一页跑通就是跑通了）、问题可定位（出锅就是这一页的锅）、进度可回滚（不行就把这一页撤了，不影响别的）。

而且它顺带解决了大文件问题。AI 一次性写整个模块，几乎必然写出巨型文件；限制成单页交付之后，配合 [D02](D02-part-extension-split.md) 的拆分术和 [G01](G01-style-guide-hard-rules.md) 的行数红线，代码规模就压住了。

#### 2. 接口不明必须问，禁止猜

这条是我认为**性价比最高**的一条规则，没有之一。

AI 最大的风险不是写错，而是**对不确定的东西"自信地编"**。它编出来的字段名、结构，往往看起来特别合理，你不去比对文档根本发现不了。等到联调那天全线飘红，两百行白写。

所以规则我写得很死：**字段不明就问，绝不猜测。** 甚至我还给了它一个提问的模板，让它照着问：

```text
【待确认】列表接口的返回结构
- 我在接口文档里没有找到 ItemModel 的分页字段定义
- 我的猜测是 { list: [], total: 0, page: 1 }，但不确定
- 请确认字段名与层级，确认前我不会开始写解析代码
```

各位看官注意最后那句——"确认前我不会开始写"。这句很关键，它把"提问"变成了一个**阻塞动作**，而不是"我先问一下，然后接着按我猜的写"。

一开始它还是会时不时手痒往下写，我就退回去让它重来。来回几次之后就稳了。

#### 3. 先出计划，再动手写

动手之前先出一份计划文档（我们习惯叫 `PLAN_xx.md`），我确认方向和几个关键决策点之后，才允许进入编码。

计划文档不用写得多漂亮，能说清楚这几件事就够：

```md
# PLAN_列表页

## 目标
实现 ItemListPage，支持分页加载与下拉刷新

## 依赖接口
- 列表查询（对应接口文档 §3.1）
- 详情查询（对应接口文档 §3.2）

## 待确认
- [ ] 分页字段名（已在【待确认】中提出）

## 决策点（需人确认）
- 筛选交互：横向滚动 chip ／ 分段控件 —— 建议前者，理由：项数不固定

## 拆分方案
- ItemListPage        页面骨架与状态
- ItemListItemCard    单条卡片（预计 120 行内）
```

这份东西的价值在哪？在于**决策提前暴露**。像"筛选到底用横滚 chip 还是分段控件"这种事，写之前定，成本是一句话；写完之后再改，成本是半天。

另外，计划文档还是个很好的对齐载体。前后端、设计那边有疑问，直接看这份，比翻代码快多了。

#### 4. 真机实测是硬门槛

这条我盯得最紧：**每个页面都必须由人真机实测并反馈，AI 说"完成"不算完成。**

原因很简单，AI 在模拟器或者 IDE 里看到的是"理想世界"：网络永远是好的，字体永远是渲染对的，权限永远是给足的。而真机上有弱网、有各种字体回退、有厂商 ROM 的骚操作、有 release 包才会暴露的问题（比如 [A01](A01-release-internet-permission.md) 那个权限坑，模拟器 debug 跑一万遍都发现不了）。

我实测的时候一般就过这么几条，各位看官可以参考：

- 首屏能不能正常出数据，空数据状态长啥样
- 断网 / 弱网下的表现，会不会一直转圈
- 反复进出页面，有没有内存或状态残留
- 打个 release 包再跑一遍（这一步千万别省）

#### 5. 文档跟代码一起走

最后一步是"三件套"：进度文档 + 踩坑文档 + 提交。

进度文档解决的是"下次接着干"的问题——AI 的上下文是会断的，人的记忆也会断，有份进度文档，第二天接着上手不用重新捋一遍。

踩坑文档（我们叫 `DEVELOPMENT_PITFALLS.md`）我认为是整套流程里**长期价值最高**的产物。它相当于团队的"第二大脑"，同类问题第二次出现的时候，直接查，不用再排查一遍。这个博客系列里的不少篇，最早就是从踩坑文档里长出来的。

### AI 适合做什么、不适合做什么

跑了一整个项目下来，我大致有了这么个判断：

- ✅ **照着接口文档实现页面**——这是它的主场，又快又稳。
- ✅ **抽公共组件、批量改样式、写样板代码**——重复劳动交给它，人做这个纯属浪费。
- ✅ **读源码定位根因**——这点常被低估。让它去翻三方库源码核对一个待确认的行为，比我自己翻快得多。
- ⚠️ **业务决策**（权限怎么划、语义怎么定）——它可以给建议，但**拍板必须是人**。
- ❌ **替代真机实测**——这个真不行，没得商量。

一句话概括：**凡是有明确输入、明确标准的活儿，尽量给它；凡是需要"负责任"的活儿，人自己来。**

### 一点没说透的话

我得实话实说，这套流程也不是没有代价。

它比"直接让 AI 写"慢。写计划、提问确认、真机实测，这些都要花时间。如果你只是搞个小 demo、验证个想法，用不着这么重，直接开写就完事儿了。

它对人的要求也不低。你得看得懂它写的东西，才谈得上"把关"；不然计划文档你也看不出问题，实测你也不知道该测什么，那流程就退化成了走形式。

所以我的建议是：**按项目体量取舍**。玩具项目别上流程，正经要维护好几年的项目，这点前期成本我觉得挺值。

### 小结

好啦，这套七步流程就聊到这儿。

复盘一下，这套东西的关键真不在"让 AI 多写点"，而在于**用流程把人的判断力插到关键节点上**：动手前插一道"计划确认"，防跑偏；写代码前插一道"接口必问"，防瞎编；交付前插一道"真机实测"，防自嗨；收尾时插一道"文档沉淀"，防重复踩坑。

四道关卡，说白了都是在补 AI 那个"不知道自己不知道"的短板。
