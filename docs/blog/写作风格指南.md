# 博文编写风格指南（FungLeo 文风手册）

> 用途：本目录下的技术博客在**调整文风**时，以此文件为唯一标准，尽量模仿 FungLeo 本人的行文习惯。
> 依据：blog.csdn.net/fungleo 上的真实文章样本（Tmux 详解、密码管理流程、Koa 长短 Token、vue2→vite 升级实录等）。
> 红线（与 `00-内容规划.md` 一致）：**只写公共技术点，不出现任何 App 业务字段、接口路径、产品名词。** 本文只管"怎么说"，不管"说什么"。

---

## 一、一句话画像

> 一个干了多年开发、爱折腾也爱吐槽的老兵，把亲历的坑和方案，用**聊天的口气、第一人称、带点自嘲和俏皮话**讲给"各位看官"听。不端着、不堆术语、不灌水，实用主义至上。

---

## 二、标志性称呼 & 口头禅（可直接套用）

这些是 FungLeo 文章里**最高频、最具辨识度**的表达，改写时务必保留几处，否则"不像他"。

### 对读者的称呼
- **「各位看官」** —— 招牌称呼，几乎每篇都有，结尾互动时必出。例："希望这篇文章能够对各位看官有所帮助"
- **「您」** —— 尊称读者，互动时用。例："耽误不了您的事儿"
- **「我们 / 大家」** —— 拉平距离，把读者当一起干活的人。例："大家还是要掌握一下"

### 口头禅 / 语气词（按场景散落使用，别一篇塞满）
- **「说实话」** —— 开头亮真实想法。例："说实话，我的编程人生也有点奇怪"
- **「好啦」「OK」「开干」** —— 收束或起势。例："好啦，我们最常用的 tmux 的使用就已经讲完了" / "开干。"
- **「闲言少叙，上代码！」** —— 铺垫完直接进代码块前的过渡。
- **「那么，…」「所以，…」「另外，…」「最后，…」** —— 口语化连接词，替代"综上所述/此外/总而言之"。
- **语气后缀「哈 / 哦 / 滴」** —— 制造轻松感。例："很忙滴""不是不可以哈""记得收藏哦"
- **反问「对吧」** —— 拉共鸣。例："你说你不会，多尴尬对吧！"

### 自嘲 / 犀利点评（技术选型类文章特别好用）
- **「被 XX 打脸」** —— 讲自己方案被推翻。例："很快被后端同学打脸"
- **「脱裤子放屁」「唬得一愣一愣的」** —— 对过度设计/故弄玄虚的毒舌点评。例："对于大多数项目来讲，都是脱裤子放屁"
- **「我感觉」「貌似」「一般而言」「可能」** —— 不用绝对词，留余地（与他 STYLE_GUIDE 禁绝对词一致）。

## 三、标题范式

观察他真实标题的共性：
1. **关键词堆砌 + 副标题补充**，用空格分隔，利于 SEO。例：`NodeJS Koa 后端用户会话管理 长短 Token 方案完整代码演示`
2. **系列化命名**。例：`一步一步配置 Ubuntu Server 的 NodeJS 服务器详细实录 7` / `vue2 + webpack 老项目升级 … 实战全记录`
3. **号召 / 情绪副标题**带感叹号。例：`… 命令行选手必备！` / `… 各位前端同学记得收藏哦！`

改写建议：
- 主标题点明技术点，副标题点明"讲什么形态"（完整代码演示 / 实战全记录 / 踩坑实录 / 方案对比）。
- 可加号召性尾巴，但**不要夸张到像标题党**，保持他"实在"的底色。
- 参考模板：`<技术点> <场景/形态>，<一句实在的副标题>`

## 四、标准文章骨架

他几乎不用 H1/H2，正文直接从 `###` 小节开始。固定三段式：

```
### 前言        ← 个人缘起 / 为什么写 / 痛点场景（必写，口语化）
### <分节 1>    ← 主体，复杂时再用 #### 细分
### <分节 2>
   #### <子节>
### 小结        ← 收束 + 点评 + 互动（必写，用「小结」而非「总结」）
```

- **前言**不是摘要，是"我为什么要写"。常用引子：
  - 个人经历切入：「我就遇到了这样的一个情况。一个五六年前基于 webpack + vue2 开发的项目，现在需要升级…」
  - 承上启下：「前面，我们通过…了解了基础概念，这篇文章，我们来讲…」
  - 直接抛痛点：「试想，你每次登录服务器…那是令人多么的闹心啊！」
- **小结**里通常做两件事：一句实在的复盘 + 一段求互动的客套话（见第九节）。

## 五、开头引入的几种套路（选一种用）

1. **个人项目背景型**（实战类最稳）：讲自己碰到的真实问题 → 决定记下来。
2. **承上启下型**（系列文）：援引前作 → 本文推进到哪一步 → "闲言少叙，上代码！"
3. **痛点共情型**：先描一个读者大概率踩过的坑/闹心的场景，再引出工具或方案。
4. **自我怀疑 / 迭代型**（适合"踩坑"主题）：抛一个自己原本以为对的方案 → 被现实/同事打脸 → 引出正题。

---

## 六、叙事弧：把"踩坑→迭代"讲成故事

他的技术文不是"结论先行"，而是**带着读者走一遍自己的弯路**，这最能形成辨识度：

> 我以为 A 方案没问题 → 被现实打脸（原因 X）→ 改成 B → 又发现 B 有隐患 → 最终落到 C。

例（密码管理文）：明文 RSA 传输 → 被后端同学指出拖库即裸奔 → 加 salt+hash → 又发现 root 被攻破仍泄密 → 前端先 hash 再加密。整篇是"我踩坑、我改、我再改"的第一人称流水账，**不端着、不假装一次写对**。

改写踩坑类文章时，优先保留这种"演进感"，别改成教科书式的"正确做法罗列"。

---

## 七、代码块规范

- **必须标注语言**：`sh` / `js` / `ts` / `json` / `dart` 等，不要裸代码块。
- **命令行带 prompt 符号**更有现场感：`$` 或 `➜ ~`。
- **代码内写中文注释**，和他一致（例 `// 长 token 有效期：15 分钟 (s)`）。
- **新旧对比**时清晰标 `// old` / `// new`（实战迁移类文章高频用法）。
- 贴完代码常接一句口语说明 + 截图引用：「如上图所示，首先…然后…最后…」
- 配置类内容（json/yaml）也走代码块，不要截图了事。

---

## 八、结尾互动句式库（直接抄，别自己编）

他每篇结尾都有固定的"求反馈 + 求赞藏"套路，改写时从下面挑一套：

- 标准版：「最后，希望这篇文章能够对各位看官有所帮助，各位看官一定要多多点赞收藏，关注留言哈！谢谢大家！」
- 轻松版：「最后，如果本文对你有所增益，希望看官您用发财的小手点个小赞哈！」
- 求点评版：「各位看官在留言区留言可以给我加分，所以希望各位看官帮帮忙，点评一下哦！当然，我们程序开发都是很忙滴，没时间点评没关系哈，点个赞，收个藏，也不是不可以哈！小可在这边谢谢各位看官了哈！」
- 抛问题版：「那么各位看官，您觉得还有没有更好的实现方式呢？」（适合方案探讨类）
- 邀交流版：「如果你也有类似的需求，并且遇到其他问题，欢迎在评论区交流。」

## 九、用词 & 语气偏好（DO / DON'T）

**DO（多用）**
- 第二人称「你 / 您」直接对话读者。
- 第一人称「我」讲亲历，不躲在"笔者"后面。
- 口语连接词：那么 / 所以 / 另外 / 最后 / 好啦 / OK。
- 适度俗语与自嘲，显真实。
- 留余地：貌似 / 感觉 / 一般而言 / 可能 / 大多数情况。
- 强调实用主义："够用就好""没必要太折腾""不适合所有项目"。

**DON'T（避免）**
- 绝对词：众所周知 / 毫无疑问 / 必须（除非真必须）/ 最（除非对比语境）。
- 学术腔、翻译腔、过度书面："综上所述""值得注意的是""鉴于此"。
- 端着：别假装方案一次写对，保留踩坑痕迹。
- 标题党式夸张、制造焦虑。
- 一长段密密麻麻不分段；他习惯短句、小段落、步骤化。

## 十一、风格自查清单（改稿时逐条过）

- [ ] 有没有 `### 前言`？是不是第一人称、带个人缘起/痛点，而不是摘要？
- [ ] 有没有出现「各位看官」至少一次？结尾互动里有没有？
- [ ] 标题是不是"技术点 + 形态/副标题"结构，没写成论文题？
- [ ] 代码块是否都标了语言？命令行是否带 prompt？有无中文注释？
- [ ] 结尾是不是 `### 小结` + 求赞/求交流句式，而非干巴巴的"总结"？
- [ ] 有没有绝对词（众所周知/必须/最）？有没有翻译腔？
- [ ] 踩坑类是否保留了"我以为→被打脸→改"的演进感？
- [ ] 全文是不是短句、小段落、能让人"聊着天读完"？
- [ ] **红线复核**：是否仍然零业务字段、零接口路径、零产品名词？
