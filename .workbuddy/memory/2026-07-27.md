## 登录时序审查：用户质疑「跳首页前先拉 profile 拿租户ID 再判公共数据」——发现 2 个真实缺陷
- 用户需求合理：登录后应先调 profile 拿**真实租户ID** → 比对是否同租户 → 判是否更新公共数据 → **完成后再跳首页**。
- 当前实践已做到「先拿租户ID、比对、清缓存、再 set state 跳首页」（auth_provider.login:116-137 是 async，UI 跳首页在 await 链之后）。但细节有 2 个 bug：
  - **Bug A（体验+白费请求）**：`login` 调 `fetchTenantId()` 时 `_ensureLoaded→_refreshFromApi` 已把 profile 的 id/name/settings 刷新进内存+磁盘；但紧接着 `onSessionChanged(crossTenant=true)→_clearTenantShared→tenantService.clearAll()` 把**刚预热好的公司数据全清了** → 首页进入时公司名必经历「空白→重拉」闪烁，且那次 profile 请求白费。修法：`_clearTenantShared` 去掉 `tenantService.clearAll()`（fetchTenantId 已刷新为正确新值，无需清）。
  - **Bug B（数据正确性/跨租户泄漏，更严重）**：`fetchTenantId()` 走 `_ensureLoaded` 受 10h TTL 短路——跨租户但缓存有效时不调 API，返回**本地旧 tenantId**；`prevTenantId`(残留旧值) == `newTenantId`(也是旧值) → `crossTenant=false` 误判同租户 → **不清理 options 缓存** → 新账号看到旧租户的归属人/分类下拉。这正是用户「必须强制拉 profile」要解的。修法：`fetchTenantId` 加 `force:true` 参数，登录路径绕过 TTL 强制拉 profile 拿真实租户ID。
- 对齐方案（待用户确认是否实施）：① `fetchTenantId(force:true)` 强制拉；② 跨租户只清 `optionsCache.clearAll()` + `invalidate(teamStatsProvider)`，**不调** `tenantService.clearAll()`；③ 用户私有任何切换都清（已有）。效果：数据正确（真实 tenantId 判定）+ 体验（公司数据登录阶段就绪无闪烁）+ 同租户保留 options 加速。
- 自动登录路径（`_tryAutoLogin:94`）用本地 token（绑定租户、不会跨租户），当前不调 fetchTenantId 不出错；为稳妥可选也走一次 `fetchTenantId(force)`，非必须。
- 状态：仅分析，未改代码。待用户确认是否实施修正（改动很小：tenant_service 加 force 参数 + cache_coordinator 去一行 + login 传 force）。
